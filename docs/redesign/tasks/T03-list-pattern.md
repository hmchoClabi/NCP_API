# T03 — 목록 화면 공통 패턴 (필터·페이지네이션·모바일 카드·행 동작)

> 선행: T02. 기준: `01-design-system.md` 5.5–5.7, 5.10절.

## 목표
모든 목록 화면을 **필터 바 + 표(모바일 카드) + 페이지네이션 + `⋯` 행 동작** 패턴으로 통일합니다.
`/history`에 이미 있는 필터·페이지네이션(build-46)을 공통 컴포넌트로 승격해 나머지 화면에 적용합니다.

## 대상과 현재 상태

| 화면 | 현재 | 적용할 필터 |
|---|---|---|
| `/portal` 보고서 보관함 | 표 3개(고객 16행 · 최근 보고서 100행 · 최근 작업 100행), 112KB, 필터 없음, 행마다 삭제 버튼 | 고객, 환경(민간/공공), 유형(일/주/월/범위), 기간, 상태, 검색 |
| `/history` 실행 이력 | 필터 3개 + 50행 페이지 | 기존(고객 `tenant_id`·검색·결과) + 방식(수동/자동), 기간 |
| `/msp/data-cleanup` | 112행, 필터 없음, "표시 항목 전체 정리 요청" | 고객, 유형, 생성일 범위, 정리 상태, 용량 하한 |
| `/msp/customers` (T02) | 카드 | env 탭 + 검색 + 상태(활성/온보딩/오프보딩) + 자동화 여부(일정 있음/없음) |
| `/msp/schedules` 등록 일정 | 8행 | 고객, 유형, 상태(활성/중지) |
| `/msp/users` | 표 2개 | 역할, 상태, 고객(`tenant_id`), 검색 |

## 작업 지시

1. **서버 공통 유틸** — `ListQuery`(필터 파싱·검증·기본값), `paginate(query, page, per_page)` → `{items, page, per_page, total, pages}`.
   `per_page` ∈ {25, 50, 100, 200}, 기본 50. 정렬 파라미터 `sort=field` / `-field` 화이트리스트.
   모든 필터는 쿼리스트링으로 받고, 잘못된 값은 무시(400 아님) + 기본값.
   T00 12절의 **기존 파라미터명은 별칭으로 계속 받습니다.** 특히 T04가 만드는 `/history?tenant_id=`, `/msp/users?tenant_id=` 링크는 반드시 필터로 적용되어야 합니다.
2. **템플릿 매크로** — `filter_bar(fields, query)`, `active_filter_chips(query)`, `pagination(page_obj)`,
   `data_table(columns, rows, row_actions=…, empty=…)`, `empty_state(icon, title, desc, action)`.
3. **`/portal` 재구성 (산출물 중심 보관함)**
   - 상단: 필터 바. 본문: 보고서 표 **하나**(고객·계정 / 유형 / 보고 기간 / 생성 시각 / 상태 / 동작). 버전 열은 T07에서 추가합니다.
   - "전체 고객" 표는 `/msp/customers`로, "최근 생성 작업" 표는 `/history`로 이동했으므로 제거하고 헤더에 링크만 남김.
   - 행 클릭 → 보고서 뷰어. 행 동작 `⋯`: 새 창에서 보기, 인쇄·PDF, 주소 복사(내부 URL). **삭제는 행에서 제거**하고 보고서 뷰어의 `⋯` 메뉴에만 둠.
     (재현 관련 동작은 T07에서 추가)
   - 상단 요약 칩: `이번 주 생성 42건 · 부분 수집 3 · 실패 1` (클릭 시 해당 필터 적용).
4. **`/msp/data-cleanup`**
   - 필터 적용 후 "선택 항목 정리 요청"만 유지. "표시 항목 전체 정리 요청"은 **필터가 하나 이상 걸렸을 때만** 활성화하고,
     확인 대화상자에 건수·예상 확보 용량·대상 고객 수를 표시 + "정리" 타이핑 확인.
   - 상단에 저장공간 미터(현재 대시보드 패널 재사용)와 보존 정책 요약.
5. **모바일 카드 전환** — `data_table`이 각 `<td>`에 `data-label`을 넣고, 컨테이너 폭 < 640px에서 카드 레이아웃(제목 행 + 상태 배지 + 라벨/값 2열).
   카드 전체가 기본 링크, 보조 동작은 `⋯`.
6. **가로 스크롤 표** — `.table-wrap`에 스크롤 위치 기반 좌·우 페이드 그림자(IntersectionObserver 또는 scroll 이벤트 + 클래스 토글),
   첫 열 sticky. build-46의 "표를 좌우로 스크롤하면…" 문구는 그림자로 대체하고 `aria-describedby`용 visually-hidden 텍스트만 남김.
7. **행 동작 메뉴** — Popover API(`popover`, `popovertarget`) 기반 `⋯` 메뉴. 메뉴 항목 키보드 이동(↑↓, Esc).
   Anchor Positioning을 쓰되 미지원 브라우저는 버튼 아래 고정 위치로 대체.
8. **고객 사용자 범위 고정** — 고객 사용자 역할로 `/portal`·`/history`에 접근하면 서버가 항상 자기 tenant로 범위를 고정하고, 고객·환경 필터는 숨깁니다.
   쿼리스트링에 다른 `tenant_id`를 넣어도 범위가 넓어지지 않아야 합니다.
9. **성능 예산** — 목록 페이지 HTML ≤ 60KB(50행 기준), DOM ≤ 1,500 노드, 서버 응답 ≤ 300ms(p95). 쿼리에 필요한 인덱스 추가(마이그레이션).

## 완료 조건
- [ ] 6개 화면 모두 필터 바·활성 필터 칩·페이지네이션 적용, 필터 상태가 URL에 유지(새로고침·뒤로가기)
- [ ] `/portal` HTML ≤ 60KB, 표 1개, 행 단위 삭제 버튼 0개
- [ ] `/msp/data-cleanup` 무필터 상태에서 "전체 정리" 비활성
- [ ] 375px에서 모든 목록이 카드로 표시되고 페이지 가로 스크롤 없음
- [ ] 빈 결과 시 빈 상태 + "필터 초기화" 동작
- [ ] 정렬·필터 파라미터 화이트리스트 테스트(SQL 주입·잘못된 값)
- [ ] `tenant_id` 및 기존 별칭 파라미터가 `/history`·`/msp/users`에서 필터로 적용됨
- [ ] 고객 사용자가 쿼리스트링 조작으로 다른 고객 데이터를 볼 수 없음(테스트)

## 검증
- 각 화면 375/1440 캡처, 필터 조합 3개 이상 시나리오 테스트, 응답 크기·시간 측정 결과 첨부.
