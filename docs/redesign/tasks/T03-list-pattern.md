# T03 — 목록 화면 공통 패턴 (필터·페이지네이션·모바일 카드·행 동작)

> 선행: T02. 기준: `01-design-system.md` 5.5–5.7, 5.10절.

## 현행 반영 (T00 결과, 2026-10-07) — 본문과 충돌하면 이 절이 우선
- **ORM이 없습니다.** `ListQuery`/`paginate`는 원시 SQL(psycopg 3)과 기존 범위 검사(고객·환경 접근 검사)를 그대로 쓰는 형태로 만듭니다.
  정렬 컬럼은 화이트리스트에서 SQL 식별자로 매핑하고, 사용자 입력을 SQL 문자열에 직접 넣지 않습니다.
- **잘못된 파라미터**: 현행 `/history`는 잘못된 `status`/`page`에 **400**, 접근 불가 `tenant_id`에 **404**를 돌려줍니다. 이 동작을 유지하고 모든 목록에 같은 규칙을 적용합니다
  (본문의 "무시 + 기본값"은 폐기). 바꿔야 할 이유가 있으면 계획에 명시하고 승인받습니다.
- `/history` 기존 파라미터 `tenant_id`, `q`(최대 200자), `status`, `page`(1–100000)를 그대로 유지합니다.
- `/msp/users?tenant_id=`는 현재 **고객 연결 폼의 사전 선택**입니다(목록 필터 아님). 이 의미를 유지하고, 사용자 목록의 고객 필터는 **새 파라미터 `customer`** 로 만듭니다.
  사용자는 여러 고객에 소속될 수 있으므로(membership) 필터는 "해당 고객에 소속된 사용자"이며, 다른 소속 정보도 함께 보여줍니다.
- 고객 목록은 경로 방식 `/msp/customers/<environment>`입니다(T02).
- **페이지 크기**: 공통 50(최대 200)은 현행 상한(포털 보고서·작업 각 100, 정리 후보 500)과 다릅니다. 화면별 변경 전후를 계획 표로 보여주고 승인받습니다.
  `/msp/data-cleanup`은 후보 상한 500을 페이지네이션으로 대체하되, 보호 조건 계산(`webapp/repository.py:2374`)이 페이지와 무관하게 정확해야 합니다.
- 템플릿 경로는 `webapp/templates/`. 상태 표시는 T01 헬퍼, 정리 상태는 01-design-system.md 5.2의 `cleanup`·`cleanup_error` kind를 씁니다.
- 보고서 유형 필터 값은 `DAILY/WEEKLY/MONTHLY/CUSTOM`(화면 라벨: 일간/주간/월간/시간 범위).

## 목표
모든 목록 화면을 **필터 바 + 표(모바일 카드) + 페이지네이션 + `⋯` 행 동작** 패턴으로 통일합니다.
`/history`에 이미 있는 필터·페이지네이션(build-46)을 공통 컴포넌트로 승격해 나머지 화면에 적용합니다.

## 대상과 현재 상태

| 화면 | 현재 | 적용할 필터 |
|---|---|---|
| `/portal` 보고서 보관함 | 표 3개(고객 16행 · 최근 보고서 100행 · 최근 작업 100행), 112KB, 필터 없음, 행마다 삭제 버튼 | 고객, 환경(민간/공공), 유형(일/주/월/시간 범위 = `CUSTOM`), 기간, 상태, 검색 |
| `/history` 실행 이력 | 필터 3개 + 50행 페이지 | 기존(고객 `tenant_id`·검색·결과) + 방식(수동/자동), 기간 |
| `/msp/data-cleanup` | 112행, 필터 없음, "표시 항목 전체 정리 요청" | 고객, 유형, 생성일 범위, 정리 상태, 용량 하한 |
| `/msp/customers/<environment>` (T02) | 카드 | 환경 탭(경로) + 검색 + 상태(`ACTIVE`/`SUSPENDED`/`ONBOARDING`/`OFFBOARDED`) + 자동화 여부(일정 있음/없음) |
| `/msp/schedules` 등록 일정 | 8행 | 고객, 유형, 상태(활성/중지) |
| `/msp/users` | 표 2개 | 역할, 상태, 고객(**새 파라미터 `customer`**; 기존 `tenant_id`는 폼 사전 선택으로 유지), 검색 |

## 작업 지시

1. **서버 공통 유틸** — `ListQuery`(필터 파싱·검증·기본값), `paginate(query, page, per_page)` → `{items, page, per_page, total, pages}`.
   `per_page` ∈ {25, 50, 100, 200}, 기본 50. 정렬 파라미터 `sort=field` / `-field` 화이트리스트.
   모든 필터는 쿼리스트링으로 받고, 잘못된 값은 현행 `/history`와 같이 **400**(접근 불가 고객은 404).
   T00 12절의 **기존 파라미터명과 의미를 유지합니다.** `/history?tenant_id=`는 목록 필터, `/msp/users?tenant_id=`는 폼 사전 선택입니다(T04가 만드는 링크도 이 의미대로).
2. **템플릿 매크로** — `filter_bar(fields, query)`, `active_filter_chips(query)`, `pagination(page_obj)`,
   `data_table(columns, rows, row_actions=…, empty=…)`, `empty_state(icon, title, desc, action)`.
3. **`/portal` 재구성 (산출물 중심 보관함)**
   - 상단: 필터 바. 본문: 보고서 표 **하나**(고객·계정 / 유형 / 보고 기간 / 생성 시각 / 상태 / 동작). 버전 열은 T07에서 추가합니다.
   - "전체 고객" 표는 `/msp/customers`로, "최근 생성 작업" 표는 `/history`로 이동했으므로 제거하고 헤더에 링크만 남김.
   - 행 클릭 → 보고서 뷰어. 행 동작 `⋯`: 새 창에서 보기, 인쇄·PDF, 주소 복사(내부 URL). **삭제는 행에서 제거**하고 보고서 뷰어의 `⋯` 메뉴에만 둠.
     (재현 관련 동작은 T07에서 추가)
   - 상단 요약 칩: `이번 주 생성 42건 · 부분 수집 3 · 실패 1` (클릭 시 해당 필터 적용).
4. **`/msp/data-cleanup`**
   - 필터 적용 후 "선택 항목 정리 요청"만 유지. "표시 항목 전체 정리 요청"은 **필터가 하나 이상 걸렸을 때만** 활성화하고,
     확인 대화상자에 건수·예상 확보 용량·대상 고객 수를 표시 + "정리" 타이핑 확인.
   - 상단에 저장공간 미터(현재 대시보드 패널 재사용)와 보존 정책 요약.
5. **모바일 카드 전환** — `data_table`이 각 `<td>`에 `data-label`을 넣고, 컨테이너 폭 < 640px에서 카드 레이아웃(제목 행 + 상태 배지 + 라벨/값 2열).
   카드 전체가 기본 링크, 보조 동작은 `⋯`.
6. **가로 스크롤 표** — `.table-wrap`에 스크롤 위치 기반 좌·우 페이드 그림자(IntersectionObserver 또는 scroll 이벤트 + 클래스 토글),
   첫 열 sticky. build-46의 "표를 좌우로 스크롤하면…" 문구는 그림자로 대체하고 `aria-describedby`용 visually-hidden 텍스트만 남김.
7. **행 동작 메뉴** — Popover API(`popover`, `popovertarget`) 기반 `⋯` 메뉴. 메뉴 항목 키보드 이동(↑↓, Esc).
   Anchor Positioning을 쓰되 미지원 브라우저는 버튼 아래 고정 위치로 대체.
8. **고객 사용자 범위 고정** — 고객 사용자 역할로 `/portal`·`/history`에 접근하면 서버가 항상 자기 tenant로 범위를 고정하고, 고객·환경 필터는 숨깁니다.
   쿼리스트링에 다른 `tenant_id`를 넣어도 범위가 넓어지지 않아야 합니다.
9. **성능 예산** — 목록 페이지 HTML ≤ 60KB(50행 기준), DOM ≤ 1,500 노드, 서버 응답 ≤ 300ms(p95). 쿼리에 필요한 인덱스 추가
   (마이그레이션은 AGENTS.md 5절 6번: 추가형·`IF NOT EXISTS`·빈 DB 2회 적용·전진 수정 계획).
